발행 파이프라인 구조도 · 2026-09-10

글 한 편이 올라가기까지

큐 폴더의 파일 하나가 Threads 게시물과 댓글 사슬이 되어 공개되기까지, 코드가 무엇을 확인하고 무엇을 막는지 열 장으로 정리했다.

발행계정
@flag_21
고정
Node 20 · CommonJS 의존성 3개 — axios · dotenv · node-cron 테스트 55개 · 네트워크 없이 실행 발행 22:00 KST · 하루 1건
01

사람이 하는 일은 파일을 넣는 것뿐

content/queue/에 파일을 두면 끝이다. 파일명 오름차순이 곧 발행 순서라 YYYY-MM-DD_ 접두어를 붙인다. 나머지는 스케줄러가 한다.

형식
JSON 또는 Markdown — 본문 1개 + 댓글 n개
선택 필드
link, publishAt — 미래면 건너뛰고 다음 파일
drafts/
승인 대기. 여기 있는 글은 발행되지 않는다
02

전체 흐름 — 잠그고, 세고, 고르고, 올리고, 옮긴다

scheduler.js ──node-cron(0 22 * * *, Asia/Seoul)──▶ index.js run()
                                                     │
  [1] 락        data/.lock {pid, startedAt}           │  pid 생존 + 나이 1시간
       │        살아있는 우리 프로세스면 → 이번 회차 skip
       ▼
  [2] 하루 상한  history.countToday() >= 1 → 종료      │  mainId 유무로 집계
       ▼
  [3] 한 건 픽   sources.fetchNext() → 파일명 순, publishAt 미래면 건너뜀
       ▼
  [4] 발행      publisher.publishThread()
       │         ├─ 검증 실패 ──────────▶ skipped-validation  (파일은 큐에 남음)
       │         ├─ 중복 ───────────────▶ skipped-duplicate
       │         ├─ 토큰 ensureValid()   계정 가드 → 만료 → 필요 시 갱신
       │         ├─ 메인 발행
       │         └─ 댓글 n개를 5초 간격으로, 각각 직전 글에 매달아 발행
       ▼
  [5] 정리      성공·중복 → content/published/     실패 → content/failed/
       ▼
  [6] 락 해제   finally — 예외가 나도 반드시 지운다
03

게시물 하나에 API를 세 번 부른다

Threads는 "바로 게시"가 없다. 컨테이너를 만들고, 준비될 때까지 기다렸다가, 그제서야 발행한다. postOne()이 이 셋을 한 묶음으로 재시도한다.

1. 생성
POST /{userId}/threads → 컨테이너 id
2. 폴링
GET /{containerId} — 1초 간격, 최대 10회
3. 발행
POST /{userId}/threads_publish → 게시물 id

고정 대기 3초 대신 상태를 확인한다. 부족하면 실패하고 넉넉하면 느려지기 때문이다.

04

댓글은 목록이 아니라 사슬이다

모든 댓글을 원글에 다는 게 아니라, 각 댓글을 직전 댓글에 매단다. 타래가 한 줄로 이어져 읽는 사람이 순서대로 따라갈 수 있다. 

메인 p1
 └─ 댓글1  reply_to_id = p1
     └─ 댓글2  reply_to_id = p2
         └─ 댓글3  reply_to_id = p3

파라미터는 reply_to_id다. 참고 가이드의 reply_to_thread_key를 쓰면 발행이 조용히 깨진다 — 계약 테스트가 이 이름을 고정한다.

05

잘못 올라가는 경우를 네 겹으로 막는다

무인 운영에서 가장 무서운 건 오류가 아니라 조용히 성공하는 사고다.

계정 가드
토큰 계정이 flag_21이 아니면 발행 거부. 우회하지 않는다
락
pid 생존 + 나이 1시간. pid는 OS가 재사용하므로 둘 다 본다
하루 상한
mainId가 있으면 1건. 댓글이 실패한 partial도 메인은 이미 공개된 상태다
중복
같은 파일명 또는 같은 본문 sha256이 이미 발행됐으면 건너뛴다
06

토큰은 스스로 연장한다

60일짜리 장기 토큰을 data/token.json에 두고, 만료가 가까워지면 발행 직전에 갱신한다. 사람이 두 달마다 손댈 일을 없앴다.

수명
60일 · 만료 7일 전부터 갱신 시도
제약
마지막 갱신 후 24시간 이내에는 API가 재갱신을 막는다
갱신 실패
기존 토큰이 유효하면 발행은 그대로 진행 계속
잔여 2일 미만
ERROR로 올리고 웹훅 알림 조치 필요
07

재시도 여부는 플래그가 정한다

오류는 threadsClient 한 곳에서 정규화되어 플래그 두 개를 단다. 호출부는 상태코드를 다시 뜯어보지 않는다.

재시도
429 · 5xx · 네트워크 · code 100 does not exist → 2s → 4s → 8s
중단
190 · 401 · 403 — 토큰 문제는 몇 번을 해도 같다

code 100은 원래 "없는 리소스"지만, 여기서 참조하는 건 방금 우리가 만든 글뿐이라 영구적 부재보다 전파 지연일 확률이 훨씬 높다.

08

실패에도 얼굴이 네 가지 있다

data/history.jsonl에 한 줄로 남는다. 어떤 얼굴이냐에 따라 사람이 할 일이 다르다.

partial
메인과 댓글 k개는 이미 공개됨. 재발행하려면 올라간 k개를 지우고 큐에 다시 넣는다
failed
아무것도 안 올라갔다. 파일은 failed/로
skipped-validation
500자 초과 등. 고칠 수 있게 큐에 그대로 남긴다
skipped-duplicate
같은 글이 이미 나갔다
09

침묵이 신호다

실패 알림은 발행을 시도해야만 울린다. 스케줄러가 죽으면 시도 자체가 없어 알림도 영영 오지 않는다. 그래서 살아 있음을 따로 보낸다.

발행 실패
partial이면 이미 올라간 댓글 개수를 함께 보낸다
토큰 임박
갱신 실패 + 잔여 2일 미만
생존 신호
주 1회(월요일 09:00) 토큰 잔여와 큐 잔량
채널
NOTIFY_WEBHOOK_URL 하나 — Slack·Discord 어디든

성공 알림은 보내지 않는다. 매일 오는 알림은 곧 무시하게 된다.

10

아직 없는 것

소스는 { fetchNext, onPublished, onFailed } 인터페이스만 맞추면 되고, 발행·이력 코드는 손대지 않는다.

2차
llmSource — Claude API로 초안 생성, 기본은 수동 승인
3차
rssSource — 네이버 블로그 RSS 폴링
미검증
link_attachment 미리보기 카드 — 이 코드 경로는 아직 한 번도 실행된 적이 없다
보류
댓글 자동 이어쓰기 — 원인이던 전파 지연이 재시도로 해소됐다
