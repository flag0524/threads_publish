## 1. 개요

### 1.1 배경
루다시스템즈는 네이버 블로그(rudatech / flag22)를 중심으로 회사 홍보와 AI 정보성 콘텐츠를 운영하고 있다. 블로그 글은 검색 유입에는 강하지만 SNS 확산력이 약하고, 매일 수동으로 Threads에 글을 올리는 것은 운영 부담이 크다. 메타가 공개한 Threads API를 이용하면 게시물 발행과 연쇄 댓글(Reply Chain) 작성을 프로그램으로 처리할 수 있으므로, 이를 자동화하여 콘텐츠 채널을 확장하고 운영 시간을 줄이고자 한다.

### 1.2 목적
개인 Windows PC에서 상시 실행되는 Node.js 프로그램이 정해진 시간에 지정된 Threads 계정(`@flag_21`)으로 게시물과 연쇄 댓글을 자동 발행한다. 1차(MVP)는 사람이 미리 작성한 큐 파일을 순서대로 발행하고, 이후 단계에서 Claude API 기반 자동 생성과 네이버 블로그 RSS 연동으로 콘텐츠 소스를 확장한다.

계정의 화자는 회사 공식 채널이 아니라 **1인칭 실무자**다. 회사 노출은 프로필 소개와 링크에만 두고 본문에서는 회사 이름을 말하지 않는다(ADR-011, [CONTENT-PLAN.md](./CONTENT-PLAN.md) 5장). 프로그램 관점에서 이 결정의 영향은 계정이 하나로 고정된다는 점이며, 잘못된 계정 발행은 FR-AUTH-06의 계정 가드가 막는다.

### 1.3 한 줄 정의
"큐에 쌓인 Threads 콘텐츠를 매일 정해진 시간에 루다시스템즈 계정으로 자동 발행하고, 발행 결과를 기록하는 프로그램"

## 2. 목표와 비목표

### 2.1 목표 (Goals)
- G1. 텍스트 게시물 1건 + 연쇄 댓글 N건을 API로 순차 발행한다.
- G2. node-cron 스케줄로 매일 1회(기본 09:00 KST) 무인 발행한다.
- G3. 단기 토큰을 장기 토큰(60일)으로 교환하고, 만료 전 자동 갱신하여 운영자가 토큰을 신경 쓰지 않게 한다.
- G4. 발행 이력을 기록하여 같은 콘텐츠가 중복 발행되지 않게 하고, 실패 시 원인을 파악할 수 있게 한다.
- G5. 콘텐츠 소스를 플러그인처럼 교체·추가할 수 있는 구조로 만들어 2차(LLM), 3차(블로그 RSS)를 큰 수정 없이 붙인다.

### 2.2 비목표 (Non-Goals)
- 이미지·동영상·캐러셀 게시물 발행 (1차 범위 제외, 확장 후보)
- 다중 Threads 계정 관리 (브랜드 계정 1개만 대상)
- 웹 UI/대시보드 제공 (CLI + 파일 기반 운영)
- 댓글 답글 모니터링·자동 응답, 좋아요/팔로우 등 인게이지먼트 자동화
- 인스타그램·X 등 다른 플랫폼 동시 발행
- Threads API 인사이트(조회수 등) 수집·분석

## 3. 대상 사용자와 시나리오

### 3.1 사용자
| 사용자 | 설명 | 주요 관심사 |
|---|---|---|
| 운영자 (본인) | 콘텐츠를 작성·승인하고 프로그램을 실행·관리하는 1인 | 손이 덜 가고, 문제가 생기면 바로 알 수 있을 것 |
| 독자 | `@flag_21` 팔로워 | 자연스럽고 규칙적인 콘텐츠 |

### 3.2 핵심 시나리오
**S1. 최초 설정**
운영자가 Meta 개발자 앱을 만들고 단기 토큰을 `.env`에 넣은 뒤 `node index.js --setup`을 실행한다. 프로그램은 장기 토큰과 사용자 ID를 발급받아 저장하고 "설정 완료"를 출력한다.

**S2. 콘텐츠 준비 (1차)**
운영자가 `content/queue/` 폴더에 게시물 파일(JSON 또는 Markdown)을 추가한다. 파일에는 본문, 연쇄 댓글 목록, 발행 희망일(선택)이 들어 있다.

**S3. 자동 발행**
매일 09:00에 스케줄러가 큐에서 발행 가능한 콘텐츠 1건을 꺼내 메인 게시물 → 댓글 1 → 댓글 2 … 순으로 발행한다. 각 발행 사이에 3~5초 대기한다. 성공하면 파일을 `content/published/`로 옮기고 이력에 기록한다.

**S4. 실패 처리**
API 오류(토큰 만료, 레이트 리밋 등)가 나면 재시도 정책에 따라 재시도하고, 최종 실패 시 파일을 `content/failed/`로 옮기며 로그와 알림(콘솔/로그 파일, 선택적으로 이메일·카카오톡)을 남긴다.

**S5. 토큰 갱신**
프로그램이 매일 토큰 잔여 기간을 확인하여 만료 7일 전이면 refresh 엔드포인트로 갱신하고 저장한다.

**S6. 수동 즉시 발행**
운영자가 `node index.js --now`로 큐 맨 앞의 발행 대상 1건을 즉시 발행할 수 있다(테스트·긴급 공지용). 특정 파일을 지정하려면 그 파일이 큐에서 맨 앞에 오도록 파일명을 조정한다(파일 인자 지정은 미지원).

**S7. LLM 자동 생성 (2차)**
운영자가 `content/topics.md`에 주제 목록만 적어 두면, 큐가 비었을 때 Claude API가 주제 1개로 게시물+댓글 초안을 생성해 `content/queue/`에 넣는다. 자동 승인/수동 승인 모드를 선택할 수 있다.

**S8. 블로그 RSS 연동 (3차)**
프로그램이 네이버 블로그 RSS(`rss.blog.naver.com/{id}.xml`)를 주기적으로 읽어 신규 글을 감지하면, 본문 요약 + 링크 + 해시태그 형태의 게시물을 생성해 큐에 넣는다.

## 4. 기능 요구사항

우선순위: **P0** 필수(MVP) / **P1** 2차 / **P2** 3차 이후

### 4.1 인증·토큰 (P0)
| ID | 요구사항 |
|---|---|
| FR-AUTH-01 | 단기 토큰을 `th_exchange_token` 방식으로 60일 장기 토큰으로 교환한다. 단기 토큰은 두 경로로 얻는다 — `.env`의 `THREADS_SHORT_LIVED_TOKEN`(탐색기 발급), 또는 `--setup --code <인증코드>`로 OAuth 인증 코드를 교환. 어느 쪽이든 결과는 `data/token.json` 한 곳에 저장한다. |
| FR-AUTH-02 | `/me` 조회로 Threads 사용자 ID와 username을 확인·저장한다. |
| FR-AUTH-03 | 장기 토큰과 발급 시각을 `.env`가 아닌 별도 파일(`data/token.json`)에 저장한다. (`.env`는 사람이 입력하는 값만 보관) |
| FR-AUTH-04 | 만료 7일 전이면 `th_refresh_token`으로 자동 갱신한다. 갱신 실패 시 경고 로그를 남기고 발행은 계속 시도한다. |
| FR-AUTH-05 | 토큰이 없거나 무효하면 발행을 중단하고 운영자에게 재설정을 안내한다. |
| FR-AUTH-06 | **계정 가드.** `EXPECTED_THREADS_USERNAME`과 토큰의 계정이 다르면 발행을 거부한다(ADR-010). 발행 직전 검사이며, `--setup` 시 불일치는 경고로 알린다. 값이 비어 있으면 검사하지 않는다. |

### 4.2 콘텐츠 큐 (P0)
| ID | 요구사항 |
|---|---|
| FR-QUEUE-01 | `content/queue/` 하위 파일을 파일명 오름차순(=날짜 접두어 순)으로 읽어 1건씩 발행한다. |
| FR-QUEUE-02 | 파일 형식은 JSON 또는 Front-matter가 있는 Markdown 두 가지를 지원한다. (형식은 TDD 참고) |
| FR-QUEUE-03 | `publishAt`(발행 희망일시)이 있으면 그 시각 이후에만 발행한다. 없으면 즉시 대상이 된다. |
| FR-QUEUE-04 | 본문 500자, 댓글 각 500자를 넘으면 발행 전에 검증 실패로 처리하고 사유를 기록한다. |
| FR-QUEUE-05 | 발행 성공 시 파일을 `content/published/`로, 최종 실패 시 `content/failed/`로 이동한다. |
| FR-QUEUE-06 | 큐가 비어 있으면 로그만 남기고 정상 종료한다(오류 아님). |

### 4.3 발행 (P0)
| ID | 요구사항 |
|---|---|
| FR-PUB-01 | 메인 게시물을 컨테이너 생성 → 발행 2단계로 게시한다. |
| FR-PUB-02 | 연쇄 댓글은 직전 게시물 ID를 `reply_to_id`로 지정하여 순서대로 게시한다. |
| FR-PUB-03 | 각 게시 사이에 설정 가능한 지연(기본 5초)을 둔다. |
| FR-PUB-04 | 컨테이너 발행 직후 상태 조회로 `PUBLISHED` 여부를 확인한 뒤 다음 댓글로 진행한다. |
| FR-PUB-05 | 각 API 호출은 최대 3회 지수 백오프로 재시도한다. 그래도 댓글 중간에 실패하면 이미 게시된 앞부분은 그대로 두고 이력에 `partial`(발행된 댓글 수 포함)로 기록한 뒤 파일을 `content/failed/`로 옮긴다. **자동 이어쓰기는 1차 범위 밖이다** — 재발행하려면 운영자가 이미 올라간 게시물을 지우고 파일을 큐에 다시 넣는다(TDD 13장 1번). |
| FR-PUB-06 | 게시물에 `link_attachment`로 URL 1개를 첨부할 수 있다(블로그 링크용, 텍스트 게시물에 한함). |

### 4.4 스케줄러 (P0)
| ID | 요구사항 |
|---|---|
| FR-SCH-01 | node-cron 표현식으로 발행 시각을 설정한다(기본 `0 9 * * *`, KST). |
| FR-SCH-02 | 하루 발행 건수 상한을 설정한다(기본 1건). |
| FR-SCH-03 | PC 재부팅 시 자동 시작되도록 Windows 작업 스케줄러 등록 절차를 문서화한다. |
| FR-SCH-04 | 실행 중 중복 기동을 막는 락 파일(`data/.lock`)을 둔다. |

### 4.5 이력·로그·알림 (P0)
| ID | 요구사항 |
|---|---|
| FR-LOG-01 | 발행 이력을 `data/history.jsonl`에 1행 1건으로 기록한다(시각, 파일명, 게시물 ID, 댓글 ID 목록, 결과, 오류). |
| FR-LOG-02 | 콘솔과 `logs/YYYY-MM-DD.log`에 동시에 로그를 남긴다. 토큰 값은 로그에 절대 출력하지 않는다. |
| FR-LOG-03 | 같은 파일명·같은 본문 해시가 이미 이력에 있으면 중복 발행을 막는다. |
| FR-LOG-04 | (P1) 최종 실패·토큰 갱신 실패 시 카카오톡 나에게 보내기 또는 이메일로 알림을 보낸다. |

### 4.6 LLM 자동 생성 (P1)
| ID | 요구사항 |
|---|---|
| FR-LLM-01 | `content/topics.md`의 주제 목록에서 미사용 주제 1개를 골라 Claude API로 게시물+댓글 초안을 생성한다. |
| FR-LLM-02 | 브랜드 톤 가이드(`content/brand-voice.md`)를 시스템 프롬프트로 사용한다. 루다시스템즈 블로그와 동일한 톤(회사 홍보 + AI 정보성, 문의 CTA 포함). |
| FR-LLM-03 | 생성 결과는 `content/drafts/`에 저장하고, `AUTO_APPROVE=true`일 때만 큐로 자동 이동한다. 기본은 수동 승인. |
| FR-LLM-04 | 생성 시 글자 수 제한·금칙어·CTA 포함 여부를 검증한다. |

### 4.7 네이버 블로그 RSS 연동 (P2)
| ID | 요구사항 |
|---|---|
| FR-RSS-01 | 설정된 블로그 ID의 RSS를 주기(기본 1시간)로 폴링하여 `data/rss-seen.json`에 없는 신규 글을 감지한다. |
| FR-RSS-02 | 신규 글의 제목·요약·링크로 게시물을 만들고(LLM 요약 선택 가능) 링크 첨부와 함께 큐에 넣는다. |
| FR-RSS-03 | 카테고리·키워드 필터로 Threads에 올리지 않을 글을 제외할 수 있다. |

### 4.8 운영 CLI (P0)
| 명령 | 동작 |
|---|---|
| `node index.js --setup` | 토큰 교환 + 사용자 ID 저장 |
| `node index.js --now` | 큐 맨 앞 1건 즉시 발행 (파일 인자 미지원) |
| `node index.js --dry-run` | 실제 API 호출 없이 큐 검증·발행 순서만 출력 |
| `node index.js --token-status` | 토큰 잔여 기간 출력 |
| `node scheduler.js` | 스케줄러 상시 실행 |

## 5. 비기능 요구사항

| 구분 | 요구사항 |
|---|---|
| 보안 | `.env`·`data/` 폴더는 `.gitignore`에 포함. 토큰은 로그·오류 메시지에 마스킹. 앱 시크릿은 토큰 교환/갱신 이외에 사용하지 않음. |
| 안정성 | API 오류 시 최대 3회 지수 백오프 재시도. 프로세스 비정상 종료 후 재기동 시 락 파일 정리 및 진행 중이던 건 재검사. |
| 레이트 리밋 | Threads API 게시 한도(24시간 기준 게시물 250건, 댓글 1,000건) 안에서 운영. 하루 1~3건 수준이므로 여유 있으나 지연 시간 준수. |
| 성능 | 게시물 1건 + 댓글 3건 발행이 1분 이내 완료. |
| 이식성 | Windows 10/11 + Node.js 20 LTS 이상. 경로 처리는 `path` 모듈 사용. |
| 관측성 | 일 단위 로그 파일, 이력 JSONL, `--token-status`로 상태 확인 가능. |
| 유지보수 | 콘텐츠 소스는 `sources/` 폴더의 모듈로 분리, 동일 인터페이스(`fetchNext()`) 구현. |

## 6. 성공 지표

| 지표 | 목표 |
|---|---|
| 무인 발행 성공률 | 30일 기준 95% 이상 |
| 운영자 개입 시간 | 주 30분 이내(콘텐츠 작성 제외) |
| 토큰 만료로 인한 발행 중단 | 0회 |
| 중복 발행 | 0회 |

## 7. 단계별 로드맵

| 단계 | 범위 | 완료 기준 |
|---|---|---|
| 1차 MVP | 토큰 교환·갱신, 큐 파일 발행, 연쇄 댓글, node-cron, 이력·로그, CLI | 7일 연속 무인 발행 성공 |
| 2차 | Claude API 자동 생성, 수동/자동 승인, 실패 알림 | 주제 목록만으로 1주일치 콘텐츠 생성·발행 |
| 3차 | 네이버 블로그 RSS 폴링, 링크 첨부 발행, 필터 | 블로그 신규 글이 24시간 내 Threads에 자동 소개 |
| 확장 후보 | 이미지 게시물, 다중 계정, 인사이트 수집, 웹 대시보드 | 별도 PRD |

---

## 8. 전제 조건 및 제약
- Meta 개발자 앱에 Threads API 액세스가 활성화되어 있고, 브랜드 계정이 Threads 테스터로 등록·수락되어 있다.
- 필요한 권한: `threads_basic`, `threads_content_publish` (링크 첨부·상태 조회 포함). 답글 관리(`threads_manage_replies`)는 1차 범위 밖.
- 스케줄러는 개인 Windows PC에서 실행되므로 PC가 꺼져 있으면 발행이 건너뛰어진다. 놓친 발행분은 다음 실행 시 "당일 상한" 안에서 순서대로 처리한다(밀린 글을 한 번에 쏟아내지 않음).
- Threads 텍스트 게시물은 500자 제한, 링크 첨부는 텍스트 게시물에만 가능하다.
- 장기 토큰은 60일 유효하며 발급 24시간 이후부터 갱신 가능하다.

## 9. 리스크
| 리스크 | 영향 | 대응 |
|---|---|---|

| API 정책·엔드포인트 변경 | 발행 실패 | API 버전 상수화, 오류 코드별 로그, 변경 감지 시 알림 |
| LLM 생성 글의 품질·사실 오류 | 브랜드 신뢰 저하 | 기본 수동 승인, 브랜드 가이드 프롬프트, 금칙어 검증 |
