## ADR-001. 런타임과 기술 스택: Node.js + axios + dotenv + node-cron

**상태**: 승인 (2026-09-02)

**배경**
원본 가이드가 Node.js 기반으로 작성되어 있고, 자사에는 Spring Boot 기반 소셜 미디어 OAuth 연동 백엔드(DADNC)도 존재한다. 개인 PC에서 1인이 운영하는 도구이므로 설치·수정이 가볍고 가이드 코드를 그대로 활용할 수 있는 스택이 유리하다.

**결정**
Node.js 20 LTS, CommonJS, `axios` + `dotenv` + `node-cron`. 외부 의존성은 최소화하고 로그·테스트·파싱은 내장 모듈로 처리한다.

**대안**
- Python (requests + APScheduler): 익숙하지만 가이드 코드를 전부 재작성해야 하고, Windows에서 상시 프로세스 관리가 Node와 다르지 않음.
- Spring Boot 백엔드에 모듈로 편입: 이미 Threads OAuth 경험이 있어 재사용 가능하지만, 개인 콘텐츠 운영 도구를 회사 B2B 파이프라인에 섞으면 배포·권한·유지보수가 무거워짐.

**결과**
가이드 코드 재사용으로 초기 구현이 빠르다. 대신 Spring Boot 백엔드의 토큰 관리 로직과는 별도로 유지해야 하며, 향후 B2B 서비스로 확장할 경우 이식 작업이 필요하다.

## ADR-002. 실행 환경: 개인 Windows PC 상시 실행 (서버·서버리스 미채택)

**상태**: 승인 (2026-09-02) — 재검토 조건 있음

**배경**
운영자 1인, 하루 1~3건 발행. 별도 서버 비용이나 GitHub Actions 설정 없이 지금 바로 시작할 수 있어야 한다.

**결정**
프로젝트 폴더(`D:\++ 2026년도 프로젝트\블로그 자동화`)에서 `node scheduler.js`를 상시 실행하고, Windows 작업 스케줄러 "로그온 시" 트리거로 자동 시작한다.

**대안**
- Linux 서버 + PM2/systemd: 가동률이 높지만 서버 준비·토큰 이전이 필요.
- GitHub Actions cron: 프로세스 상시 실행이 필요 없고 무료지만, 큐 파일을 저장소에 커밋해야 하고 토큰을 Secrets에 두어야 하며, cron 지연(수 분~수십 분)이 있음.

**결과**
PC가 꺼져 있으면 그날 발행이 누락된다. 이를 완화하기 위해 TDD 7절의 "일 상한 내 순차 소화" 규칙을 둔다. **재검토 조건**: 30일 성공률이 95% 미만이거나 발행 건수가 하루 3건을 넘으면 Linux 서버로 이전한다(코드 변경 없이 `.env`·`data/` 이동만으로 가능하도록 경로를 `path`로 처리).

## ADR-003. 토큰 저장 위치: `.env`가 아닌 `data/token.json`

**상태**: 승인 (2026-09-02)

**배경**
가이드는 장기 토큰과 사용자 ID를 `.env`에 수동으로 붙여 넣도록 안내한다. 그러나 60일마다 자동 갱신하려면 프로그램이 토큰을 스스로 저장해야 하고, `.env`를 프로그램이 덮어쓰면 사람이 관리하는 값(앱 ID·시크릿)과 뒤섞여 사고 위험이 있다.

**결정**
`.env`에는 사람이 입력하는 값(앱 ID, 시크릿, 최초 단기 토큰)만 둔다. 장기 토큰·사용자 ID·발급/만료 시각은 프로그램이 `data/token.json`에 기록·갱신한다. `data/`는 `.gitignore`에 포함.

**대안**
- `.env` 자동 덮어쓰기: 파일 하나로 단순하지만 주석·다른 키가 훼손될 수 있음.
- Windows 자격 증명 관리자 / DPAPI 암호화: 더 안전하지만 Node에서 추가 네이티브 의존성이 필요. 1인 PC 환경에서는 과도.

**결과**
갱신 로직이 단순해지고 `--token-status`로 상태 확인이 쉽다. `data/token.json`은 평문이므로 폴더 공유·클라우드 동기화 금지 규칙을 README에 명시한다.

## ADR-004. 스케줄링 방식: node-cron 인프로세스 + Windows 작업 스케줄러 자동 시작

**상태**: 승인 (2026-09-02)

**배경**
발행 시각 지정(매일 09:00)과 재부팅 후 자동 재시작이 필요하다.

**결정**
발행 스케줄은 `node-cron`(timezone `Asia/Seoul`)으로 프로세스 내부에서 관리하고, 프로세스 자체는 Windows 작업 스케줄러가 로그온 시 실행한다. 중복 기동 방지용 락 파일을 둔다.

**대안**
- Windows 작업 스케줄러가 매일 09:00에 `node index.js`를 직접 실행(상시 프로세스 없음): 가장 단순하지만 3차 RSS 폴링(1시간 주기)까지 작업을 여러 개 등록해야 하고, 스케줄 변경 시 코드가 아닌 OS 설정을 바꿔야 함.
- PM2 + pm2-windows-startup: 재시작·로그 관리가 편하지만 전역 설치 의존성이 늘어남. 선택 사항으로 남긴다.

**결과**
스케줄이 코드(`.env`의 `POST_CRON`)에 있어 버전 관리·이식이 쉽다. 프로세스가 죽으면 다음 로그온까지 재시작되지 않으므로, 예기치 않은 종료는 로그로 확인해야 한다(PM2 도입 시 해소).

## ADR-005. 콘텐츠 소스의 단계화와 플러그인 구조

**상태**: 승인 (2026-09-02)

**배경**
콘텐츠 소스로 수동 큐 파일, Claude API 자동 생성, 네이버 블로그 RSS 세 가지를 모두 원한다. 한 번에 구현하면 MVP가 커지고 검증이 늦어진다.

**결정**
1차는 큐 파일만, 2차 LLM, 3차 RSS 순으로 단계화한다. 모든 소스는 `sources/` 아래 동일 인터페이스(`fetchNext / onPublished / onFailed`)를 구현하고, LLM·RSS 소스는 최종적으로 **큐 파일을 생성**하는 방식으로 큐를 단일 발행 경로로 삼는다.

**대안**
- 각 소스가 직접 발행: 경로가 셋으로 갈라져 중복 방지·이력·승인 로직이 소스마다 반복됨.
- DB(SQLite) 큐: 정합성은 좋지만 운영자가 메모장으로 글을 고치는 워크플로우와 맞지 않음.

**결과**
운영자는 항상 `content/queue/` 폴더만 보면 "내일 무엇이 올라가는지" 알 수 있다. 소스 추가 시 발행·이력 코드는 손대지 않는다. 대신 큐 파일 파싱 규칙(JSON/Markdown)이 사실상 내부 API가 되므로 형식을 안정적으로 유지해야 한다.

## ADR-006. LLM 공급자: Claude API (Anthropic), 기본은 수동 승인

**상태**: 승인 (2026-09-02)

**배경**
2차 단계에서 주제만 주면 게시물과 댓글을 생성해야 한다. 브랜드 계정에 올라가는 글이므로 품질과 사실성 통제가 중요하다.

**결정**
`@anthropic-ai/sdk`로 Claude를 호출하고, 브랜드 톤 가이드(`content/brand-voice.md`)를 시스템 프롬프트로 사용한다. 생성물은 `content/drafts/`에 두고 기본은 **수동 승인**, `AUTO_APPROVE=true`일 때만 큐로 자동 이동한다.

**대안**
- OpenAI API: 기능상 동등. 이미 Claude Code로 개발 워크플로우를 구성하고 있어 계정·과금 창구를 하나로 유지하는 쪽을 택함.
- 자사 온프레미스 LLM: 비용은 없지만 개인 PC에서 호출하려면 망 접근 설정이 필요하고, 짧은 SNS 카피 품질은 상용 모델이 유리.

**결과**
API 비용이 발생하지만 하루 1건 수준이면 미미하다. 수동 승인이 기본이므로 "완전 무인"은 아니며, 채택률 70% 이상이 안정적으로 나오면 자동 승인으로 전환을 검토한다.

## ADR-007. 네이버 블로그 연동: RSS 폴링 (파이프라인 직접 연결 미채택)

**상태**: 승인 (2026-09-02)

**배경**
블로그 신규 글을 Threads에 소개해야 한다. 같은 폴더에 블로그 자동화 프로세스가 있으므로 그 파이프라인과 직접 연결하는 방안도 가능하다.

**결정**
공개 RSS(`rss.blog.naver.com/{id}.xml`)를 1시간 주기로 폴링하고, `data/rss-seen.json`으로 신규 글을 판별한다. 첫 실행 시 기존 글은 모두 seen 처리한다.

**대안**
- 블로그 작성 파이프라인과 직접 연결: 발행 즉시 반영되지만 두 시스템이 강하게 결합되어 한쪽 변경이 다른 쪽을 깨뜨림. 블로그 글이 실제로 공개된 뒤에만 Threads에 올려야 하는데, 파이프라인 단계에서는 공개 여부를 보장하기 어려움.
- 수동 링크 등록: 자동화 효과가 없음.

**결과**
최대 1시간 지연이 생기지만 블로그 시스템과 완전히 분리된다. RSS에는 본문 전체가 실리지 않을 수 있으므로 요약 품질은 `description` 길이에 의존하며, 필요 시 LLM 요약을 붙인다.

## ADR-008. 발행 안정화: 고정 대기 대신 컨테이너 상태 확인 + 재시도

**상태**: 승인 (2026-09-02)

**배경**
가이드는 댓글 사이에 3초 고정 대기로 "타이밍 이슈"를 완화한다. 그러나 대기 시간이 부족하면 실패하고, 넉넉하면 불필요하게 느려진다.

**결정**
컨테이너 생성 후 `GET /{container_id}?fields=status`로 `FINISHED`를 확인한 뒤 발행하고, 게시 간에는 레이트 리밋 완화용 지연(기본 5초)을 별도로 둔다. 실패는 지수 백오프 3회 재시도, 컨테이너 생성 성공 후 publish 실패는 같은 `creation_id`로 재시도한다.

**대안**
- 고정 대기만 사용: 구현이 단순하지만 원인 파악이 어렵고 간헐적 실패가 남음.

**결과**
API 호출이 건당 1~2회 늘지만 실패 원인이 `error_message`로 남고, 성공률이 높아진다.

## ADR-010. 발행 계정 가드: `EXPECTED_THREADS_USERNAME` 불일치 시 발행 거부

**상태**: 승인 (2026-09-07)

**배경**
토큰은 `data/token.json` 한 곳에서 읽고, 재발급·계정 전환·다른 앱의 토큰 복사 등으로 파일의 계정이 바뀔 수 있다. 무인 발행이므로 잘못된 계정에 글이 올라가도 사람이 바로 알아채지 못하며, 브랜드가 아닌 개인 화자로 운영하는 계정(ADR-011)이라 오발행의 회수 비용이 크다. 발행 자체는 성공하므로 오류 로그로도 잡히지 않는다.

**결정**
`.env`의 `EXPECTED_THREADS_USERNAME`과 토큰의 `username`을 대소문자 무시하고 비교하여, 다르면 발행을 중단한다(`token.assertExpectedAccount`). 검사 지점은 **발행 직전 `ensureValid()`** 이며, 오류는 `isAuthError`로 올려 재시도하지 않는다. `--setup`에서 불일치를 발견하면 저장은 하되 `ERROR` 로그로 경고한다(토큰 발급 자체는 정상 동작일 수 있으므로). 값이 비어 있으면 검사하지 않으며, `.env.example`은 `flag_21`을 채워 배포한다.

**대안**
- 검사하지 않음: 코드가 한 줄 줄지만, 오발행은 조용히 성공하는 유일한 사고 유형이라 사후 탐지가 어렵다.
- 사용자 ID로 비교: username 변경에 영향받지 않아 더 엄격하지만, 운영자가 `.env`에서 눈으로 확인할 수 없는 값이라 설정 실수를 유발한다.
- `--setup`에서만 1회 검사: 이후 토큰 파일이 교체되는 경우를 잡지 못한다.

**결과**
계정을 의도적으로 바꾸려면 `data/token.json` 삭제 + `--setup` 재실행이라는 명시적 절차를 밟아야 한다. 이 가드는 **우회하지 않는다** — 테스트 계정으로 실험할 때도 `.env` 값을 바꿔서 진행한다. username을 바꾸면 `.env`도 함께 고쳐야 발행이 재개된다.

## ADR-011. Threads 계정의 화자: 브랜드 채널이 아닌 1인칭 실무자

**상태**: 승인 (2026-09-07)

**배경**
초기 PRD(v0.1)는 이 계정을 "루다시스템즈 브랜드 계정"으로 전제했다. 그러나 운영 계획을 세우며 확인한 것은, Threads에서 회사 화자의 홍보성 글은 도달이 낮고 팔로워가 늘지 않는다는 점이다. 1차 목표는 리드 확보가 아니라 도달·팔로워 성장이다.

**결정**
화자를 "공공기관에 AI 넣는 사람"이라는 1인칭 실무자로 두고, 회사 노출은 프로필 소개와 링크에만 남긴다. 본문에서 회사 이름을 말하지 않고, 제품 소개·무료 진단 CTA는 본문에 넣지 않는다. 전환은 프로필과 마지막 댓글에서만 유도한다([CONTENT-PLAN.md](./CONTENT-PLAN.md) 5장).

**대안**
- 브랜드 공식 계정 화자: 회사 인지도에 직접 기여하지만, 초기 팔로워가 없는 상태에서는 도달이 나오지 않아 자동 발행 자체가 무의미해진다.
- 계정 2개 운영(브랜드 + 개인): 프로그램은 다중 계정을 지원하지 않고(비목표), 1인 운영에서 콘텐츠가 양쪽 다 얇아진다.

**결과**
발행 대상 계정이 `@flag_21` 하나로 고정되므로 ADR-010의 계정 가드가 실효적인 안전장치가 된다. 콘텐츠 검수 기준(회사명 미노출, 링크 빈도 10편 중 1~2편, 해시태그 1~2개)은 코드가 아니라 큐 파일 작성 단계에서 사람이 지킨다 — 프로그램은 글자 수와 금칙어만 검증한다.

## ADR-012. 실패 알림: 채널을 고정하지 않는 범용 웹훅 1개

**상태**: 승인 (2026-09-08)

**배경**
무인 발행이므로 실패를 사람이 알아야 한다. 특히 토큰 갱신 실패는 로그를 안 보면 만료될 때까지 아무 신호가 없다. 원래 미결 사항은 "카카오톡 나에게 보내기 vs SMTP" 중 하나를 고르는 것이었다.

**결정**
채널을 코드에 박지 않는다. `.env`의 `NOTIFY_WEBHOOK_URL` 하나만 두고 `core/notify.js`가 axios로 POST 1회를 보낸다. 값이 비어 있으면 알림 기능은 꺼진 것과 같다. 페이로드는 `{ text, content }` 두 키를 함께 담아 Slack(`text`)과 Discord(`content`)를 동시에 만족시킨다. 알리는 사건은 **발행 실패·partial**과 **토큰 갱신 실패 + 잔여 2일 미만** 두 가지뿐이고, 성공 알림은 보내지 않는다.

**대안**
- 카카오톡 나에게 보내기 API: 휴대폰에 바로 뜨지만 카카오 OAuth 토큰을 별도로 저장·갱신해야 해서 `core/token.js`급 관리 코드가 하나 더 생긴다. 알림 하나 받자고 만료되는 자격 증명을 늘리는 셈이다.
- 이메일(SMTP): 가장 보편적이지만 `nodemailer` 의존성이 붙어 "외부 의존성 3개" 원칙(ADR-001)이 깨진다.
- 채널별 어댑터 레이어: 지금 채널이 하나도 확정되지 않은 상태에서 인터페이스부터 만드는 것은 과설계다.

**결과**
신규 의존성 0으로 알림이 붙고, 채널 결정이 코드가 아니라 `.env` 한 줄로 미뤄진다. 대신 채널별 리치 포맷(버튼·첨부·멘션)은 못 쓰고 평문 한 덩어리만 보낸다. 카카오톡으로 받고 싶으면 카카오워크 웹훅을 쓰거나, 그때 가서 ADR을 새로 쓴다. 알림 실패는 삼키므로 "알림이 안 온 것"과 "사고가 없는 것"을 구분하려면 여전히 로그를 봐야 한다.

## ADR-014. 오류 100 "does not exist"를 재시도 대상으로 분류

**상태**: 승인 (2026-09-07, 문서화 2026-09-08)

**배경**
첫 실전 발행(2026-09-07 05:47)에서 메인 게시물은 올라갔는데 첫 댓글이 오류 100 "The requested resource does not exist"로 실패해 `partial`로 끝났다. 같은 파일을 곧바로 재발행하니 댓글 4개가 모두 성공했다. 방금 발행한 메인 게시물 id가 아직 API에 전파되지 않은 상태에서 `reply_to_id`로 참조한 전파 지연이었다.

**결정**
`normalizeError`에서 **코드 100이면서 메시지가 `does not exist`에 매칭될 때만** `isRetryable`로 분류한다(코드 100 전체가 아니다 — 100은 잘못된 파라미터에도 쓰이므로). 재시도는 기존 백오프(2s→4s→8s)를 그대로 탄다. 이 파이프라인이 참조하는 리소스는 방금 우리가 만든 것뿐이므로 영구적 부재보다 일시적 지연일 확률이 훨씬 높다.

**대안**
- 댓글 전 고정 대기를 늘린다: 매 발행이 느려지고, 지연이 그보다 길면 여전히 실패한다(ADR-008과 같은 이유로 기각).
- 재시도하지 않고 자동 이어쓰기로 해결한다: 사고를 막는 게 아니라 사고 후 복구를 만드는 것이라 순서가 뒤바뀐다(TDD 13-1 보류 근거).

**결과**
발행 성공률이 올라가고 TDD 13-1(자동 이어쓰기)의 착수 근거가 약해졌다. 대신 진짜로 삭제된 리소스를 참조하는 경우에도 3회 재시도로 최대 14초를 낭비한다 — 무인 배치라 문제되지 않는 비용으로 본다. 영문 메시지에 매칭하므로 API가 문구를 바꾸면 조용히 재시도가 꺼진다. `test/threadsClient.test.js`가 이 분류를 고정한다.
