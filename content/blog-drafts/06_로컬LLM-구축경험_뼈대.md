### 남의 구축 사례를 열 개 읽는 것보다

온프레미스 LLM 이야기를 하다 보면 결국 같은 질문에 닿습니다.

> "그래서 우리 환경에서 되나요?"

이 질문에 자료로 답하기가 어렵습니다. 공개된 구축 사례는 대개 결과만 있고, 무엇을 잘못 골랐다가 되돌렸는지는 나오지 않기 때문입니다.

그래서 저희가 직접 세운 과정을 그대로 적어두려고 합니다. 잘된 것보다 **되돌린 것** 위주로 썼습니다.

### 왜 직접 세웠나

`[ 사내에 로컬 LLM을 구축하게 된 이유. 예: 고객사 환경을 그대로 재현해보기 위해 / 외부 API를 쓸 수 없는 검증 업무가 생겨서 / 교육·데모용으로 필요해서 ]`

`[ 그 전에는 어떻게 하고 있었는지 한 문장 ]`

### 구성

지금 돌아가고 있는 구성입니다.

| 항목 | 사양 |
|---|---|
| 모델 | `[ 모델명과 파라미터 규모 ]` |
| GPU | `[ 카드 종류와 장수 ]` |
| 서버 | `[ CPU·메모리·저장장치 대략 ]` |
| 추론 엔진 | `[ vLLM / Ollama / llama.cpp 등 ]` |
| 용도 | `[ 문서 검색 / 요약 / 내부 실험 등 ]` |
| 구축 기간 | `[ 약 O주 ]` |

`[ 이 구성으로 정착하기까지 몇 번 바꿨는지, 처음 구성은 무엇이었는지 ]`

### 모델을 고른 기준

큰 모델이 항상 답은 아니었습니다. 실제로 확인한 순서는 이렇습니다.

**1. 한국어 문서를 제대로 읽는가**
영어 벤치마크 점수는 참고가 되지 않았습니다. `[ 실제로 테스트에 쓴 문서 종류 — 예: 회의록 5건, 조례 3건 ]`을 넣어보고 답을 비교했습니다.

**2. 우리 GPU에 올라가는가**
`[ 처음 시도했다가 메모리 때문에 포기한 모델이 있다면 그 이야기 ]`

**3. 동시 사용자를 견디는가**
혼자 쓸 때는 다 잘 돕니다. `[ 동시 접속 몇 명까지 테스트했는지, 응답 속도가 어떻게 변했는지 ]`

`[ 최종적으로 그 모델을 고른 결정적 이유 한 문장 ]`

### 예상보다 오래 걸린 곳

**`[ 가장 시간이 많이 들어간 작업 ]`**

`[ 왜 오래 걸렸는지, 처음에 얼마로 잡았고 실제로 얼마가 걸렸는지 ]`

저희가 다시 한다면 여기에 처음부터 `[ ]`만큼을 잡을 겁니다.

### 되돌린 결정

`[ 처음에 이렇게 했다가 바꾼 것 1 — 무엇을, 왜 되돌렸나 ]`

`[ 처음에 이렇게 했다가 바꾼 것 2 ]`

이 두 가지는 자료만 봐서는 알기 어려운 부분이었습니다. 직접 세워보고 나서야 보였습니다.

### 지금 돌려보고 아는 것

**되는 것**
`[ 실제로 만족스럽게 쓰고 있는 작업 — 예: 긴 문서 요약, 내부 문서 검색, 초안 생성 ]`

**아직 안 되는 것**
`[ 기대했지만 품질이 부족했던 작업 ]`

**외부 서비스와 비교하면**
`[ 체감 차이. 어떤 작업에서 차이가 크고 어떤 작업에서 거의 없는지 ]`

이 구분이 중요합니다. 온프레미스는 외부 서비스의 완전한 대체가 아니라 **되는 범위가 다른 선택지**입니다. 그 범위를 알고 들어가야 실망하지 않습니다.

### 구축을 검토하신다면

저희 경험에서 나온 순서입니다.

1. **쓸 업무를 세 개 적습니다.** 이게 없으면 장비 규모를 정할 수 없습니다
2. **그 업무의 문서로 모델을 먼저 테스트합니다.** 빌리든 임대하든, 장비를 사기 전에 합니다
3. **동시 사용자 수를 정합니다.** 5명과 50명은 완전히 다른 견적입니다
4. **그다음에 장비를 정합니다**

이 순서를 뒤집어 장비부터 사면 `[ 겪었거나 목격한 결과 — 예: 안 쓰는 서버가 남습니다 ]`.
